# 商品名确认节点开发与联调说明

首次阅读代码可先看同目录《商品名确认节点代码阅读与示例》；源码中的【00】～【09】注释对应从入口、检索、评分到最终输出的完整调用顺序。

## 已实现范围

第一版实现单轮商品名确认：DeepSeek 结构化提取 → BGE-M3 查询编码 → Milvus dense/sparse 混合检索 → 按每个目标确认 → 输出查询范围或澄清信息。

当前最小图只有 `START → item_name_confirm → END`，不生成商品知识问答，也不调用正文检索、HyDE、Web 或重排。可选历史由调用方传入，没有 MongoDB 会话存储；候选选择暂通过重新提交完整商品名完成。

## 入口及调用链

```text
processor/query_processor/__main__.py 或 main_graph.run_item_name_confirm
  → ItemNameConfirmNode.process（输入校验、错误边界、日志）
  → ItemNameExtractor.extract（查询专用 DeepSeek 链，独立 1200-token 预算）
  → QueryEmbeddingService.embed（encode_queries，复用导入 BGE-M3 模型）
  → ItemNameSearchRepository.search（只读检查/加载/混合检索）
  → ItemNameAligner.align（每个商品表述的评分判定）
  → ItemNameAligner.aggregate（全目标汇总及原问题绑定）
```

业务配置位于 `knowledge/processor/query_processor/config.py`；查询模型位于 `knowledge/schema/query_models.py`；提示词位于 `knowledge/prompt/query_prompt.py`。底层连接、模型名称、集合配置沿用 ImportConfig，查询不执行导入全流程校验，也不会创建缺失的业务集合。

## 运行方式

项目根目录执行：

```powershell
$env:PYTHONIOENCODING='utf-8'
& '.\knowledge\.venv\Scripts\python.exe' -m knowledge.processor.query_processor 'RS PRO RS-12 数字万用表怎么测电阻？'
```

依赖 `knowledge/.env` 中的 DeepSeek、BGE-M3 和 Milvus 配置；需要先完成商品名导入，并启动 Milvus。技术错误退出码为 1，正常确认、澄清和无匹配退出码为 0，具体结果查看 `item_confirm_status`。

程序调用：

```python
from knowledge.processor.query_processor.main_graph import build_query_graph

# 常驻服务复用编译图及节点，避免每次查询重新校验并加载集合。
graph = build_query_graph()
result = graph.invoke({
    "original_query": "RS-12 怎么测电阻？",
    "request_id": "query-001",
    "history": [],
})
```

单次便捷入口为 `run_item_name_confirm(state, config=None)`。`request_id` 可省略，入口自动生成；允许字母、数字、下划线和连字符。`session_id` 可选，不自动读取历史。可选 `history` 的每条消息包含 `role`（user/assistant）和 `content`，最多 10 条、合计 8000 字符；问题最多 2000 字符。

## 评分和确认规则

| 项目 | 行为 |
| --- | --- |
| 自动确认门槛 | **融合分数 >=0.7**，不接受请求或环境变量覆盖 |
| 向量通道 | `dense_vector/COSINE` + `sparse_vector/IP`，与导入索引一致 |
| 融合 | `WeightedRanker(0.5, 0.5, norm_score=True)` |
| 候选下限 | 默认 0.45 |
| 竞争候选分差 | 默认 0.15；与同一表述的第二个候选比较，不限第二名必须 >=0.7 |
| 同名多文档 | 保守规范化后合并；组分数取最大值，不累加文档票数 |
| 型号冲突 | 明确的型号后缀/字母/数字冲突进入澄清 |
| 多目标 | 全部确认才发布 `item_names`；部分成功保存在 `confirmed_items` |
| 纯品类词 | 无具体型号/可靠上下文时澄清，不猜具体产品 |
| 问题改写 | 使用已确认名称绑定原表述，原问题全文保留，不使用提取草稿覆盖用户意图 |

分数不做客户端二次归一化，阈值前不四舍五入。分差通过 `Decimal(str(score))` 比较十进制边界。0.7 不是“70% 正确概率”。

两路与融合 TopK 共用初始值 50；返回满额且末位仍在候选范围时，有界扩至 100、200。到上限仍满额则标记 `candidate_recall_truncated` 并澄清。最多展示 5 个候选，在各未解决目标间轮流分配；完整候选与诊断保留在 `mention_results`。

可配置环境变量：

```dotenv
QUERY_ITEM_MID_CONFIDENCE=0.45
QUERY_ITEM_SCORE_GAP=0.15
QUERY_ITEM_TOP_K=50
QUERY_ITEM_MAX_TOP_K=200
QUERY_LLM_MAX_TOKENS=1200
```

更换融合权重、metric、向量模型或服务端版本必须重新验收分数契约。本期固定等权，不提供权重调参环境变量。

## 输出与下游使用

| 状态 | 含义 | 可进入正文检索 |
| --- | --- | --- |
| `confirmed` | 全部目标已确认；`item_names`、`rewritten_query` 有值 | 是 |
| `needs_clarification` | 无具体名称、近分歧义、型号冲突、部分确认或召回截断 | 否 |
| `not_found` | 全部提取目标均无有效候选 | 否 |
| `error` | 输入、模型、向量、集合或检索服务错误 | 否 |

下游使用 `route_after_item_confirm` 或等价的显式状态门禁，不能只看 answer 是否为空。每次执行都清理旧的商品范围、候选、改写和错误码；依赖异常会清空本次部分成功结果，不冒充“没找到商品”。

`confirmed_items` 包含库内名称、融合分数以及 `matched_pks`、`matched_document_ids`、`file_titles`。这些 document_id 仅来自本次 TopK 命中，不代表该商品全部文档；以后正文检索需要按名称补齐完整文档范围或引入 product_id 映射。

目前没有商品主数据 ID，无法仅凭同名识别两个真实产品的身份冲突；库内同名必须指向同一业务商品。正则型号检查只覆盖同时含拉丁字母和数字的明显型号，不能代替别名和产品主数据治理。

日志沿用 `logging`，使用 `query.*` 前缀；记录 request_id、mention_id、数量、决策原因和耗时，不记录完整用户问题、历史、向量、密钥或底层异常正文。调试详细结果可查看节点返回值。

## 测试与验收命令

```powershell
# 纯本地查询测试，不连接模型或数据库。
& '.\knowledge\.venv\Scripts\python.exe' -m unittest knowledge.test.test_item_name_confirm -v

# 全项目回归；真实外部服务用例默认跳过。
& '.\knowledge\.venv\Scripts\python.exe' -m unittest discover -s knowledge/test -p 'test_*.py' -q

# 真实 Milvus：临时集合与已知向量，验证评分归一化及查询仓储。
$env:RUN_QUERY_MILVUS_INTEGRATION='1'
& '.\knowledge\.venv\Scripts\python.exe' -m unittest knowledge.test.test_query_milvus_integration -v

# 完整查询：调用 DeepSeek、加载 BGE-M3，仅向随机临时集合写测试商品。
$env:RUN_QUERY_FULL_INTEGRATION='1'
& '.\knowledge\.venv\Scripts\python.exe' -m unittest knowledge.test.test_query_full_integration -v
```

两个真实测试均以 `it_query_*` 随机集合隔离，结束后清理自己的集合，不写业务集合。Windows 沙箱可能限制 tempfile 创建目录后的访问；若全量回归出现临时目录 PermissionError，应在具有临时目录权限的终端运行，不通过修改业务代码规避。

## 当前限制

导入和查询仍沿用现有项目约束：导入期间暂停同文档查询。Strong 读取不能提供商品集合和切片集合的跨集合事务。后台并发发布、完整会话恢复、HTTP 查询接口及聊天前端是后续工作。

真实小样本通过只能证明链路和关键行为可用；50 条以上标注集的准确率、覆盖率及性能验收仍需业务数据，不把初始参数声明为已完成业务调优。
