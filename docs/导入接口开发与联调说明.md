# 导入接口开发与联调说明

日期：2026-09-07

## 启动与页面

前端位于 `knowledge/front/import.html`，普通 HTML 无构建依赖。后端按模块绝对路径定位页面，不依赖启动目录。在项目根目录执行：

```powershell
uv sync --project knowledge
& .\knowledge\.venv\Scripts\python.exe -m uvicorn knowledge.api.main:app --host 127.0.0.1 --port 8000 --workers 1
```

页面：`http://127.0.0.1:8000/import`；OpenAPI：`http://127.0.0.1:8000/docs`。

也可以在 `knowledge` 目录运行 `uv run uvicorn knowledge.api.main:app --app-dir .. --host 127.0.0.1 --port 8000 --workers 1`。其中 `--app-dir ..` 保证 Python 可以找到现有的 knowledge 包。

## 按代码阅读流程

1. `knowledge/api/main.py`：只装配应用、跨域、生命周期和业务异常到 HTTP 的转换。
2. `knowledge/api/import_routes.py`：接收上传/查询参数，调用服务并返回结果；响应字段定义在 `import_schemas.py`。
3. `knowledge/service/import_service.py`：检查文件、分块落盘、预留队列名额、提交任务和清理过期文件。它接收普通文件流，不依赖 FastAPI。
4. `knowledge/service/import_task_facade.py`：单工作线程取任务，原件归档后调用图。
5. `knowledge/processor/import_processor/main_graph.py`：tracked 包装器报告节点开始/结束/失败，复用现有业务节点。
6. `knowledge/service/task_store.py`：持短锁更新状态，GET 返回副本，前端每 1.5 秒查询。
7. `knowledge/service/import_artifact_service.py`：归档 Markdown 原始版、处理版和图片，写 manifest。
8. 门面仅在图和归档均成功后标记 completed。失败则记录失败步骤，保留部分结果及本地任务目录。

上传链路可直接按 `import_routes.upload → ImportService.upload → ImportTaskFacade.submit` 阅读。请求体接收限额属于 HTTP 协议处理，独立放在 `api/upload_middleware.py`；文件内容与磁盘容量规则属于业务，放在 service 中。同步上传路由由 FastAPI 在线程池执行，接口不需要自己编写线程调度代码。

服务通过 FastAPI 的 `Depends` 注入：`main.py` 在应用启动时创建 ImportService，`api/dependencies.py` 的 `get_import_service` 返回该实例，路由用 `service: ImportService = Depends(get_import_service)` 接收。方法体直接调用 `service.upload(...)` 或 `service.get_status(...)`，不再通过 Request 查找服务。应用关闭时统一关闭服务；这与 Spring 管理并注入单例 Bean 的使用思路相似。测试可通过 `app.dependency_overrides[get_import_service]` 替换服务。

参数和配置校验集中在 `knowledge/schema/import_models.py`：

- `UploadParameters` 使用 `Field` 检查文件名的类型、长度和非法字符，使用 `field_validator` 检查扩展名、保留文件名以及 document_id 的 UTF-8 字节长度，并去除 ID 两端空白。
- `ImportSettings` 使用 `PositiveInt` 检查上传上限、队列容量、保留时间和磁盘阈值。环境变量默认值也执行校验，配置错误在启动时暴露。
- `ImportService.upload` 在预留队列前构造 `UploadParameters`，验证失败转为既有接口错误消息；不支持的扩展名仍返回 415，其他非法参数返回 422。
- 实际文件内容、文件字节数、磁盘空间和队列状态仍在服务中检查，Pydantic 校验器不执行网络或磁盘操作。

约束写法使用 Pydantic 的字段及校验器机制，可参考[官方 Validators 文档](https://docs.pydantic.dev/latest/concepts/validators/)。

按用户最新要求保持简单：未引入独立 TaskExecutor、Observer 继承体系或链式 Builder。ImportTaskFacade 是真实门面；Queue 内置在门面内，观察者是一个回调，归档清单用字典逐步组装。所有节点仍可不带观察者从 CLI 调用。此处是对原技术方案中组件拆分的简化，业务流程没有省略。

## 接口

`POST /upload`，multipart 字段 file，另可填写 document_id。默认按文件 SHA-256 生成文档 ID；更新已有文档时显式复用 ID。响应含 task_id、document_id、status_url、total_steps、poll_interval_ms。

`GET /status/{task_id}` 返回 queued/processing/completed/failed，以及 steps、done_list、running_list、skipped_list、durations、progress_percent、result、error。进度是步骤占比，不是时间预测。PDF 10 步，Markdown 9 步。错误示例：文件过大 413、格式不支持 415、参数非法 422、接纳容量满 429、未知任务 404。

默认同源页面无需跨域；独立前端来源通过 `CORS_ALLOW_ORIGINS` 白名单配置，预检由 CORSMiddleware 处理，不允许跨域 Cookie。业务接口不返回全文、向量和凭据。

## 文件与向量关联

原始文件位于 `imports/{document_id摘要}/{task_id}/original/`；转换结果位于同前缀 converted/；manifest.json 保存对象大小与 SHA-256。图片节点已有展示对象使用 `knowledge/{task_id}/` 独立目录，完整图片归档另存 converted/images/，防止同名文档互相覆盖。

Milvus 的既有 JSON metadata 增加 source_archive，关联原件、两版 Markdown、manifest 和 task_id，无需改变固定 schema。历史记录缺少该字段仍兼容。临时绝对路径只用于诊断，长期追溯使用对象键。

原始 Markdown 在图片处理前另存 `.raw`，避免 md_path 更新以及 `_new` 文件名影响原始备份。原上传文件与工作副本物理分离。成功归档后清理任务工作目录，失败目录默认保留 24 小时，清理周期 60 秒。

## 运行边界

- 仅单进程支持内存任务，不支持重启续跑；重启后旧 task_id 返回 404。
- 默认单文件 100 MiB、队列 10 个等待任务、临时目录接纳阈值 5 GiB。阈值是接纳检查，不是对 PDF 转换膨胀量的文件系统硬配额。
- 请求体接收限额包含额外 1 MiB multipart 开销；文件自身仍单独限制。
- MinIO/Milvus 无跨库事务。最终归档失败时，result 仍可表明 vector_status=verified；前端显示失败，不自动删除已写向量。
- 本地存储关闭时当前任务只有 5 秒宽限，强制退出不保证后台任务完成。关闭时排队任务标记失败。
- MD 本地图片未一起上传时，仅报告缺失引用；不虚构图片已归档。
- 部署默认监听 127.0.0.1，当前未加用户登录，适合本地联调。
